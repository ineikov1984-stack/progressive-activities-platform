# CODEX.md — как работи Codex в този проект

Прочети това веднъж в началото на всяка сесия, след `AGENTS.md`. Целта е да вземаш задачи от WORKBOARD и да ги довеждаш до зелен PR **без** излишни въпроси, нови спецификации и планове за одобрение. Собственикът не е програмист. Той решава продуктови въпроси и прави merge — не одобрява планове.

## 1. Десетте правила

1. **Спецификацията вече е написана.** За всяка задача в WORKBOARD има файл в `docs/product/` и решения в `docs/process/DECISIONS.md`. Не пиши нова спецификация и не пускай brainstorming.
2. **Не питай собственика за неща, които са в спецификацията или в DECISIONS.** Питай само при истински продуктов въпрос, който липсва:
   - най-много 3 въпроса наведнъж;
   - всеки с варианти и с препоръка, отбелязана „(препоръчвам)“;
   - отговора записваш в DECISIONS в същия PR.
3. **Планът е кратък** — до 15 реда в описанието на PR-а. Никой не го одобрява. Не пиши файлове с планове (`docs/superpowers/**`, `outputs/**`).
4. **Работи директно.** Без subagent-driven-development за бърза и стандартна скорост; при строга — виж т. 2.
5. **Дизайн само по одобрените макети** в `docs/design/mockups/`. Нов екран без макет → спри и питай (WORKFLOW т. 3).
6. **Проверката е CI.** Локално пускаш само засегнатите тестове. Не повтаряй пълни проверки „за всеки случай“.
7. **Една задача = един клон `codex/<кратко-име>` = един PR.** Ред в WORKBOARD преди старт; махаш го след merge.
8. **Към собственика:** на български, кратко, без технически думи. Накрая — точните команди за пускане (т. 8).
9. **Не пипай горещ файл, който е зает в WORKBOARD** (AGENTS.md → „Горещи файлове“).
10. **Сигурността от AGENTS.md е неотменима:**
    - tenant и RLS; чужд tenant → 404;
    - без лични данни в логове;
    - само синтетични данни;
    - без нови зависимости без нужда.

## 2. Superpowers — какво да ползваш и какво не

| Skill | Ползвай ли | Как |
|---|---|---|
| `brainstorming` | **Не** за задачи от WORKBOARD | Само ако собственикът поиска нова идея без спецификация. Тогава кратки въпроси, а спецификацията пише Claude (с ревю на архитект). |
| `writing-plans` | Само наум | До 15 реда в описанието на PR-а: стъпки, засегнати файлове, тестове. Без файл, без одобрение. |
| `executing-plans`, `subagent-driven-development` | Само при **строга** скорост и голяма задача | При бърза и стандартна скорост — директно. |
| `test-driven-development` | **Да** при строга скорост | API, права, миграции, детски данни: първо тестът, после кодът. |
| `systematic-debugging` | Да | При червен CI: прочети анотациите и поправи конкретния ред. |
| `verification-before-completion` | Да, но кратко | Проверяваш по „Готово, когато“ от задачата и по т. 7 тук. Без нови, измислени проверки. |
| `requesting-code-review` | Веднъж на PR при строга скорост | Независим ревюър (отделна сесия или агент, който не е писал кода) по `docs/process/reviewers/security.md`. Един кръг. Поправките ги проверяваш ти, по списъка. |
| `finishing-a-development-branch` | Да, до PR | Merge **не** правиш — прави го собственикът. |

**Скоростите** (AGENTS.md → „Три скорости“):
- **бърза** — текстове, токени, документи;
- **стандартна** — екран върху готово API;
- **строга** — права, миграции, RLS, детски данни, писма, публично API.

Архитектът вече е прегледал спецификациите за задачите в т. 9. Не повтаряй това ревю.

## 3. Цикълът на една задача

```bash
git fetch origin && git switch -c codex/<име> origin/main
# 1. Ред в docs/process/WORKBOARD.md → „В работа“: агент, клон, области, горещи файлове → commit "docs: ..."
# 2. Код + тестове
# 3. Локално само засегнатото:
cd platform/apps/api && php artisan test --filter=<Име> && composer lint && composer analyse
cd platform && pnpm --filter @progressive/web lint && pnpm --filter @progressive/web typecheck && pnpm --filter @progressive/web test
node platform/scripts/check-docs.mjs
# 4. push и PR по шаблона в т. 8; чакаш CI (api, web, e2e, docker, secrets)
# 5. Червено → анотациите на проверката → поправка → push
# 6. Строга скорост → едно ревю по сигурност → поправки → push
# 7. Съобщение до собственика с командите (т. 8)
```

**Ако задачата е започната от Claude и е спряла по средата:** редът в WORKBOARD казва клона. Клонът е push-нат. Продължи в същия клон и отбележи в реда, че я продължаваш.

**Ако `main` се промени и PR-ът има конфликт** (почти винаги е в `WORKBOARD.md` или `DECISIONS.md`): `git merge origin/main`, оправяш реда и push-ваш. PR с конфликт не пуска CI.

## 5. Архитектура — следвай съществуващото

### API (`platform/apps/api`, Laravel 13, PHP 8.4, PostgreSQL 17)
- **Домейни:** `app/Domain/{Identity,Organizations,Catalog,Enrollment,Audit}`.
  - **Actions** пишат — транзакция, заключвания, версия, 409.
  - **Services** четат и пазят правилата.
  - Домейн вика само Actions и Services на друг домейн, никога таблиците му. Пример: Catalog не чете `enrollments`. Контролерът сглобява резултата от двата домейна (виж `ScheduleController`).
- **HTTP:** тънки контролери в `app/Http/Controllers/Api/V1`; форматът на отговора е в `app/Http/Presenters`; маршрутите са в `routes/api.php` (горещ файл), в групите `tenant` + `organization.access:operational.read|write`.
- **Tenant:**
  - `ResolveTenant` слага `TenantContext` и `app.current_organization_id` от проверено членство (header `X-Organization-Id`);
  - моделите имат global scope;
  - `DB::table(...)` винаги с изрично `organization_id`;
  - таблицата `children` няма RLS — минавай през `enrollments`.
- **Права:**
  - `TeamAbilities`, `StaffRights` (роля плюс добавки със срок), `AccessScope` (`groups`, `scheduleGroups`, `scheduleChildren`), `TeachingScope` (своите групи и заместване);
  - всеки нов маршрут влиза в `tests/Feature/Organizations/TeamRightsCharacterizationTest.php` и в `TeamRightsNarrowScopeTest.php`, иначе CI пада;
  - операторът на платформата не действа от името на организацията (`role->isTeam()`).
- **Миграции:**
  - нов файл с текуща дата и час; вече merge-нати миграции не се пипат;
  - започва с проверката за ролята-собственик — копирай я от последната миграция;
  - нова таблица: `organization_id`, RLS `ENABLE` + `FORCE`, изричен `REVOKE`/`GRANT` за `progressive_app`, без DELETE;
  - миграцията е обратима и има тест (образец `StaffMembersMigrationTest`, с `--path`).
- **Писма:** през `enrollment_events` в същата транзакция; worker-ът ги праща. Без лични данни в логове.
- **Одит:** `AuditRecorder` — само кой, какво, кога, без свободен текст с лични данни.

### Уеб (`platform/apps/web`, Next.js 16, React 19, TypeScript strict)
- `src/features/<област>/`:
  - `api.ts` — fetch с `X-Organization-Id`, по образеца на `features/schedule/api.ts`;
  - `presentation.ts` — чиста логика с unit тестове;
  - компоненти и `*.module.css`.
- Страниците са в `src/app/dashboard/<област>/page.tsx`. Shell-ът и менюто са в `features/dashboard`; менюто се строи по `access` от контекста.
- Образци за повторно ползване:
  - `features/schedule/` — панел, долен лист, филтри, combobox, бърз преглед при посочване;
  - `features/team/` — списък и профил;
  - `features/enrollment/contact-reveal.tsx` — „Покажи телефона“ с одит.
- Без нови зависимости. `globals.css` и `tokens.css` са горещи файлове.

## 6. Дизайн и UX — задължително

Общият приет стил и моделите за бъдещи оформления са в `docs/design/WORKSPACE-UX.md`. Следвай ги заедно със спецификацията и одобрения макет.

- **Токените** от `src/design-system/tokens.css`:
  - текст: `--ink`, `--ink-body`, `--ink-muted`;
  - действия: `--action`, `--action-hover`;
  - повърхности: `--surface*`, `--border*`, `--focus`;
  - състояния: `--status-available|limited|last|full|info` (+ `-soft`);
  - цветове за дейностите: `--cat-art|science|sport|music|language`;
  - отстояния: `--space-1..20`; радиуси: `--radius-*`; `--control-height`.
- **Без hex в нов код.**
- **Шаблони, които вече ползваме:**
  - страничен панел на компютър; долен лист под 900 px;
  - Esc затваря, а фокусът се връща там, откъдето е отворен панелът;
  - skeleton при зареждане; кратък текст и „Опитай пак“ при грешка;
  - празно състояние с изречение, не с празен екран.
- **Бутоните:** показват се само действията, които човекът има право да направи. Не ги правим сиви.
- **WCAG 2.2 AA:**
  - видими етикети и фокус;
  - контраст;
  - състоянието е и с думи, не само с цвят;
  - цели ≥ 44 px;
  - ARIA шаблони (combobox, dialog) по APG.
- **Mobile-first:** проверка на 390, 768 и 1440 px, без хоризонтален скрол на страницата. Часовете са по София (`Intl`, `timeZone: 'Europe/Sofia'`).
- **Текст:**
  - на български, ясен, без технически думи (`tenant`, `catalog.view` и подобни не се показват);
  - думите от речника в DECISIONS: „Присъства“, „Отсъства“, „Предупредено отсъствие“, „Премахни“ (не „Махни“);
  - без граматически род, когато не знаем кой е човекът;
  - примери с суми — в евро.
- **Адреси:** в адреса никога няма лични данни. Например `child=<uuid>`, а не името.

## 7. Тестове — капаните, които вече сме хванали

- **`TenantContext`:** изчиства се след всяка заявка в тестовете. Избери организацията отново или ползвай `withoutGlobalScopes()`; проверявай броя обновени редове.
- **Вмъкване на няколко реда наведнъж:** всички редове трябва да имат едни и същи ключове.
- **Помощни методи:** не ги кръщавай като методите на `TestCase`.
- **`tenant-isolation`:** тестовете в групата пипат истински чужди данни — втора организация със своя група и дете, включително едно и също дете в две организации.
- **PHPStan** е строг: без излишни `=== null` или `is_string`, които са „винаги верни“; типовете в docblocks да са точни (`list<…>`, `array{…}`).
- **Тестовете вървят на SQLite.** Затова RLS и `ILIKE` се доказват с отделен тест на PostgreSQL като `progressive_app` (образец `StaffRightsSchemaTest`, `MembershipActivitySchemaTest`).
- **Часове и дни:** тествай смяната на часа (последната неделя на октомври и на март) и границите на деня по София.
- **Брой заявки:** където има списък, тествай, че броят заявки не расте с броя редове (3 срещу 30).

## 8. Шаблони

**Описание на PR:**
```
## Какво
…
## Защо
… (спецификация, точка)
## План (до 15 реда)
…
## Как е проверено
тестове …; CI; за UI — screenshot на 390 и 1440
## Рискове
…
```

**Съобщение до собственика, когато PR-ът е зелен** — винаги така, без изключения:
```
PR #N (<какво, с обикновени думи>) е готов за merge.
Какво да направите (от папка platform):
1. Merge на PR #N в GitHub.
2. git pull
3. docker compose up --build -d
4. (само ако има миграция) docker compose exec api php artisan migrate --database=pgsql_admin --force
Какво да пробвате: …
```
- **Няколко готови PR-а наведнъж** — първо пишеш **реда на merge** („първо #A, после #B“) и защо, ако има зависимост. Командите даваш **веднъж** накрая, за всички.
- PR, който е само документи, не иска команди. Пиши „след merge не е нужно да пускате нищо“.
- Ако няма какво да се пуска, пиши „Сега няма какво да пускате“.
- Миграцията е **отделна** стъпка и пише ясно „задължително този път“. Seed е „по желание“.
- Ако след merge друг PR има конфликт (обикновено в `WORKBOARD.md`), оправяш го ти и казваш на собственика да изчака CI. Той не оправя конфликти.

## 8а. Предаване на работата — когато лимитът свършва

Когато усетиш, че лимитът ти свършва (или собственикът каже „спри“), **преди** да спреш:

1. **Нищо не остава само локално.** Commit на всичко, дори недовършено (`wip: …`), и push на клона.
2. **Отвори PR като draft**, ако още няма. В описанието добави раздел:
   ```
   ## Състояние (предаване)
   Готово: …
   Остава: … (по точки от спецификацията)
   Следваща стъпка: … (файл, тест, команда)
   CI: зелен / червен — коя проверка и защо
   Решения, които взех сам: …
   ```
3. **WORKBOARD:** в реда си в „В работа“ смени статуса на „спряно — предадено“, с клона, PR-а и следващата стъпка. Commit и push.
4. **Съобщение до собственика** (точно така):
   ```
   Спирам — лимитът ми свършва. Работата е запазена в PR #N (клон codex/…).
   Кажи на Claude: „Продължи PR #N по реда в WORKBOARD.“
   Сега няма какво да пускате.
   ```

Claude (или Codex, когато Claude спре) продължава в **същия клон** (WORKFLOW т. 7), прочита „Състояние (предаване)“ и реда в WORKBOARD и не започва отначало.

## 9. Задачите за Codex сега

**„График“ е завършен** (#98, #102, #103, #104). Следват два етапа. Спецификациите са готови, прегледани от архитект и с отговорите на собственика (DECISIONS 01.11.2026). Работиш по реда, **един PR наведнъж**, защото почти всички пипат `routes/api.php` или миграции — горещи файлове.

### 9.1 „Присъствия“ — `docs/product/attendance.md` — **започни оттук**
Разделянето е в т. 9 на спецификацията (8 PR-а); за всеки има „Готово, когато“. Накратко:
1. **Данни и права:**
   - миграцията с четирите таблици и тригера за пропуска;
   - границата от 15 минути в промените на графика (поправя и `schedule-changes.md`, т. 4.1);
   - `TeachingScope::teachesSession`, `AttendanceAccess`.
   
   Строга; **ревю по сигурност на PR-а**.
2. **Списъкът на заниманието** и стесняването на `RecordVisitOutcome`. Строга.
3. **Отметките:** „Всички присъстват“, ключ за повторение с `applied`, 409, `40P01`/`55P03`, поправка след срока. Строга.
4. **Заниманието:** тема, „Не се проведе“ и „Проведе се“, в същия маршрут. Строга.
5. **„Днес“, „Чакат отбелязване“** и полетата в графика. Строга.
6. **Месецът** (офисът, и учителят за своите групи) и присъствията в картата на детето. Строга.
7. **Уеб за учителя** по макетите `Main`, `MarkA`, `ChildSheet`, `History`. Стандартна.
8. **Уеб за офиса:** `Admin`, бутонът в графика, „Не се проведе“. Стандартна; **UX ревю веднъж** върху екраните от 7 и 8.

В края на етапа: независимо ревю по сигурност върху PR 2–8.

**Решенията, които не бива да се изпускат:**
- до края на следващия **календарен** ден (за петък — събота), после само собственик или администратор с причина;
- отбелязването започва **15 минути преди** началото;
- „Предупредено отсъствие“ се смята от пропуска;
- дете в пауза може да е „Присъства“;
- напомнянето е само на екрана;
- родителят не вижда присъствията до етап 6;
- учителят вижда месеца на своите групи (назначение или водещ на предлагането), но не и на тези, в които само замества.

### 9.2 „Търся заместник“ — `docs/product/substitute.md` — след „Присъствия“
Разделянето е в т. 10 на спецификацията — PR 1, 2, 3а, 3б, 4, 5, всеки с „Готово, когато“.

- **1:** миграцията, изричното „замества“ в графика, стесняването на `TeachingScope`. Строга; **ревю по сигурност на PR-а**.
- **2:** API на учителя и писмото до офиса. Строга.
- **3а:** API на офиса — списък, отказ, кой е свободен. Строга.
- **3б:** назначаването като `action: substitute` в промените на графика. Без нов маршрут. Строга; накрая **ревю по сигурност на етапа**.
- **4:** уеб за учителя. Стандартна.
- **5:** уеб за офиса — „Какво ви чака“, диалогът, „Замести учител“ в панела, „Назначи заместник“ в лентата. Стандартна; **UX ревю веднъж** за 4 и 5.

**Решенията (т. 2.3):**
- помощникът също може да поиска заместник;
- родителите не получават писмо;
- имейл за нова заявка получават всички, които могат да назначават;
- зает колега се назначава с потвърждение по ключове;
- при „Премести“ заместникът остава.
- **Блокерът от ревюто** (т. 12) — назначаването на заместник не изтрива чакащи писма за други промени — **има задължителни тестове**.

Следващите етапи — профил на детето, счетоводна основа, възнаграждения — още нямат спецификация. Не започвай код; Claude пише спецификацията. Запиши в WORKBOARD → „Въпроси към собственика“, че си стигнал дотук.
